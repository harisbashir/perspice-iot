# Perspice IoT — Sub-project 3: Alarms & Notifications Implementation Plan

> **For agentic workers:** execute task by task. Each task is test-first (write the failing test, see it fail, implement, see it pass) and ends with one conventional commit. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Ship v0.3.0: platform admins (and permitted customer admins) define alarm rules per profile, device or customer; the `rules` role evaluates them on every telemetry and status event and raises, de-duplicates and clears alarms; operators see, acknowledge and comment on alarms live; recipients are notified by email, in-app and web push according to their own preferences, with digests during alarm storms; webhooks deliver alarm events to other systems; dashboards can be emailed as PDF reports on a schedule.

**Architecture:** builds on v0.2.0. New server modules `alarms` (rules CRUD, evaluator, engine, alarm API), `delivery` (channel interface, dispatcher queue, preferences, digest, web push, webhooks, delivery log) and `schedules` (scheduled reports, reusing the reports/renderer pipeline). The `rules` role consumes the existing `events:device` stream; the `scheduler` role runs time-based checks (duration timers, no-data, digests, report schedules). Web: alarms pages, rule editors, notification settings, service worker for push, and the alarm widgets reserved in sub-project 2.

**Tech additions:** `web-push` (VAPID; keys already generated by `cli vapid-keys`), `cron-parser` (report schedules, with timezone), service worker (plain `public/sw.js`, no PWA framework yet).

**Spec:** `docs/superpowers/specs/2026-10-08-perspice-iot-design.md` §6 (alarms & notifications), §7.2/7.3/7.5 (alarm data source and widgets), §11 (webhooks, timezones), §12 (retries, dead letters), §13 row 3.

## Scope decisions

| Item | Decision |
|---|---|
| Rule types | `threshold`, `range`, `duration`, `rate_of_change`, `state_match`, `status`, `no_data_key` now. `geofence` (needs location, sub-project 5) and `maintenance_due` (generator features, sub-project 5) are reserved in the type union and rejected with "not available yet". |
| Telemetry used for evaluation | Values from the `telemetry` event (the latest value per key in the message); `rate_of_change` keeps the previous sample in rule state. Historic back-evaluation is out of scope. |
| Existing status notifications (`profile.statusNotify`) | Kept for compatibility, but sent through the new dispatcher so preferences, push, digests and the delivery log apply. Profiles can move to `status` alarm rules; docs explain the difference (notification only vs. an alarm with a lifecycle). |
| Timezones | Added now: `user.timezone`, `customer.timezone` (IANA, default `UTC`), needed by rule schedules, quiet hours and report schedules. |
| Scheduled report format | PDF dashboard reports (sub-project 2 renderer) and CSV/XLSX exports of a widget, delivered by email as a signed link (no attachments; links last 7 days for scheduled reports). |
| SMS / chat channels | Out of scope (spec §14); the channel interface allows them later. |

## Global Constraints

- **Scope:** a rule is visible and editable only within its tenant. Platform users write profile, device and customer rules; customer admins with `alarm.rule.write` write rules only for their own customer (customer-level, or device-level on their own devices). Effective rules for a device = enabled profile rules (minus those the device or its customer disabled) + device rules + customer rules for the device's customer.
- **Recipients** resolve only to active users who can see the device (its customer's users, or platform users). A hand-edited rule can never notify another tenant's users (Review Focus 2).
- **One active alarm per (rule, device)**, enforced by a partial unique index; concurrent workers converge (Review Focus 1).
- **Flapping:** every rule has a clear condition with a margin (hysteresis) and an optional minimum active time; notifications have a per-(rule, device) cooldown.
- **Delivery:** every send goes through BullMQ (`notify` queue) with 5 attempts and exponential back-off; permanent failures are kept in `delivery_log` with status `dead` and shown in the admin delivery log.
- **Preferences:** in-app notifications are always stored; email and push respect the user's channels, minimum severity and quiet hours (critical alarms can be set to bypass quiet hours).
- **Webhooks:** HTTPS only (HTTP allowed only by a platform setting), no private, loopback or link-local destinations unless allowed by a platform setting, 5 s timeout, no redirects, HMAC-SHA256 signature header, secrets encrypted at rest with the master key (Review Focus 3).
- **New permissions:** `alarm.read` (all roles with `device.read`), `alarm.ack` (operators and admins), `alarm.rule.write` (platform admins; customer admins), `webhook.manage` (platform admins; customer admins for their own customer), `report.schedule` (users with `export.data`).

## Review Focus

1. **Duplicate and flapping alarms** — two rules workers process the same device concurrently; a value oscillates around the threshold. Expect: exactly one active alarm per (rule, device); clear only below threshold − margin; at most one notification per cooldown. Tests in Tasks 4 and 5.
2. **Cross-tenant rules and recipients** — customer A writes a rule against B's device or lists B's users as recipients; A's admin reads B's alarms. Expect: 404 / validation error; alarms list and data source exclude B; recipients outside the device's tenant are dropped. Tests in Tasks 3, 6, 7.
3. **Webhook SSRF and secrets** — a webhook pointing at `http://127.0.0.1:3000/internal/...`, `169.254.169.254`, a DNS name resolving to a private address, or a redirect to one. Expect: refused at save and at send time (resolved address checked, redirects not followed); the secret is never returned after creation. Tests in Task 11.
4. **Notification storms** — 200 alarms in a minute for one user. Expect: the first N individual notifications, then one digest email; in-app items all stored; quiet hours hold email/push until they end (or drop to the digest). Tests in Task 10.
5. **Scheduled reports after access changes** — the owner of a schedule is deactivated or loses access to the device/customer. Expect: the run is skipped and recorded as failed with a reason, nothing is sent. Tests in Task 12.

### Task 5: Rules engine

**Files:** `engine.consumer.ts`, `alarms.service.ts`, `timers.job.ts`
- Rules role consumes `telemetry` and `device.status_changed` events; loads effective rules (cached by profile version); keeps state in Redis per (rule, device); raise = insert alarm (`ON CONFLICT DO NOTHING` on the partial index) + `raised` event + dispatch; clear = update + `cleared` event + dispatch; publishes `alarm` events to Redis for WebSocket fan-out (`alarm:{customerId}` / platform). Scheduler job every 10 s fires due duration timers and `no_data_key` checks.
- [ ] Integration tests: telemetry above threshold raises once; repeated values don't duplicate; two consumers racing produce one alarm (**Review Focus 1**); clear below margin; offline status rule; no-data after N s; disabled rule and opt-out respected; latency from publish to alarm < 2 s.
