# Perspice IoT — Sub-project 4: Operations Implementation Plan

> **For agentic workers:** execute task by task. Each task is test-first (write the failing test, see it fail, implement, see it pass) and ends with one conventional commit. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Ship v0.4.0: encrypted, verified backups with exactly-one retention (schedule, back up now, download, upload & restore, CLI); an S3-compatible storage driver; Prometheus metrics with an optional monitoring profile (Prometheus + Grafana) and an admin System page; AWS IoT Core as an alternative MQTT transport with an AWS compose profile; and a measured load test against success criterion 8 (10,000 devices at 1 message / 10 s on 4 vCPU / 8 GB, p95 ingest-to-dashboard latency < 2 s).

**Architecture:** builds on v0.3.0. New server modules `backups` (archive format, backup/restore jobs on a `maintenance` queue in the scheduler role, maintenance mode), `system` (heartbeats, status, metrics registry) and `aws` (IoT provisioning, IoT Core ingest client, data-plane command publisher). `StorageDriver` gains an `s3` implementation. Deploy gains `docker-compose.aws.yml`, a `monitoring` profile, and a load-test override that pins resource limits.

**Tech additions:** `@aws-sdk/client-s3` + `@aws-sdk/s3-request-presigner`, `@aws-sdk/client-iot` + `@aws-sdk/client-iot-data-plane`, `prom-client`, `tar-stream`; zstd from Node 24's `zlib`; PostgreSQL 16 client tools in the server image (PGDG apt). Tests: MinIO testcontainer, `aws-sdk-client-mock`.

**Spec:** `docs/superpowers/specs/2026-10-08-perspice-iot-design.md` §5.5 (AWS IoT Core), §10.1–10.6 (storage, backups, deployment, scripts, observability), §1.3 criterion 8, §13 row 4.

## Scope decisions

| Item | Decision |
|---|---|
| Backup engine location | In the server (scheduler role) so the admin UI can back up and restore; the CLI (`perspice backup`, `perspice restore <file>`) runs the same code through `cli.js`. `pg_dump`/`pg_restore` come from the PostgreSQL 16 client in the server image (path configurable, so tests run them through Docker). |
| Backup passphrase | `BACKUP_PASSPHRASE` in `.env`, generated by `install.sh` (added by `update.sh` when missing) and shown to the operator once. Never written into a backup. The master key is included only with `BACKUP_INCLUDE_MASTER_KEY=true`. |
| Archive | `perspice-backup-<version>-<timestamp>.pbk`: a tar (manifest, `database.dump`, `storage/…`, optional `config.env`), zstd-compressed, AES-256-GCM-encrypted with a scrypt-derived key. One file kept, at `backups/latest.pbk` in storage. |
| Restore | Online: maintenance mode (API answers 503 except health and restore status; the web shows a banner), restore into a side database, swap, restore storage files, run migrations forward, leave maintenance. Same major version only; older minor runs migrations; newer is refused. |
| "Platform alarm" on backup failure | Platform admins get a critical notification (in-app + email) and the System page shows the failure. (Alarms are device-scoped.) |
| AWS IoT Core | Implemented against the AWS SDK and tested with SDK mocks plus a local MQTT broker standing in for the IoT endpoint (lifecycle topics simulated). A live check against a real AWS account is documented as a manual step (`scripts/test.sh --live-aws`), not run in CI. |
| Load test | Run locally on the compose stack with per-service CPU/memory limits summing to 4 vCPU / 8 GB, simulator on the same host. Results recorded in `docs/load-test.md`. |

## Global Constraints

- Backups never contain export files, earlier backups, or the backup passphrase. Retention is exactly one: a new backup is written to a temporary key, verified (decrypts, GCM tag valid, archive lists, manifest checksums match), then replaces the previous one. A failed backup leaves the previous one untouched (Review Focus 2).
- Only `backup.manage` (super admin) can back up, download, restore or change the schedule. Downloads use short-lived signed links. Uploaded backups go to a private storage key and are deleted after the restore (Review Focus 1).
- Restores never leave a half-restored database: the dump restores into `perspice_restore` and replaces `perspice` only after `pg_restore` succeeds (Review Focus 3).
- `/metrics` is served on each process's internal health port and the API's internal network only; Caddy never proxies it.
- AWS: device private keys are returned once and never stored; the IoT policy limits each thing to its own `perspice/v1/<thingName>/…` topics (Review Focus 4).

## Review Focus

1. **Backup confidentiality and integrity** — a stolen backup file, a tampered byte, a wrong passphrase, an attacker downloading backups. Expect: unreadable without the passphrase; tampering detected before anything is restored; download needs `backup.manage` and a signed link; no secrets beyond what the operator opted into. Tests in Tasks 4, 5.
2. **Exactly-one retention under failure** — `pg_dump` fails, storage fills up, two backups start at once. Expect: previous backup intact and still downloadable; one backup at a time; platform admins notified. Tests in Task 5.
3. **Restore safety** — a backup from a newer version, a corrupt archive, an archive with `../` paths, a failure halfway through. Expect: refused before maintenance mode, or rolled back with the live database untouched; maintenance mode always lifted. Tests in Task 6.
4. **AWS certificate and policy scope** — a device certificate used to publish on another device's topics, or the private key retrieved later. Expect: the policy restricts each thing to its own topics; the key exists only in the creation response. Tests in Task 9.
5. **Success criterion 8** — sustained load at the target on constrained resources. Expect: no message loss, p95 publish-to-dashboard latency < 2 s, stable memory. Measured in Task 12.

### Task 1: Contracts and configuration

**Files:** `packages/shared/src/system.ts`, `apps/server/src/config/config.ts`, `deploy/env.example`

- Config: `STORAGE_DRIVER=local|s3` with `S3_BUCKET`, `S3_REGION`, `S3_ENDPOINT`, `S3_ACCESS_KEY_ID`, `S3_SECRET_ACCESS_KEY`, `S3_FORCE_PATH_STYLE`; `BACKUP_PASSPHRASE`, `BACKUP_INCLUDE_MASTER_KEY`, `PG_DUMP_PATH`, `PG_RESTORE_PATH`; `MQTT_TRANSPORT=emqx|aws-iot` with `AWS_REGION`, `AWS_IOT_ENDPOINT`, `AWS_IOT_POLICY_NAME`, `AWS_IOT_CERT_PATH`/`KEY_PATH`/`CA_PATH`; `METRICS_ENABLED`.
- [ ] Tests: config validation (s3 requires bucket; aws-iot requires endpoint), schedule/status schemas.
- [ ] Commit `feat(shared): operations contracts and configuration`.

### Task 3: Metrics and heartbeats

**Files:** `apps/server/src/system/*`, ingest metrics, `main.ts`

- Heartbeats: every process writes `heartbeat:<role>:<instance>` (version, start time, pid) to Redis every 10 s with a 30 s TTL.
- [ ] Tests: `/metrics` text format includes the expected series and counts a published message; heartbeat appears and expires; `/metrics` not reachable through the public API prefix.
- [ ] Commit `feat(system): Prometheus metrics and process heartbeats`.

### Task 4: Backup archive format

**Files:** `apps/server/src/backups/archive.ts`
- Streaming writer: tar (`tar-stream`) → zstd → AES-256-GCM (scrypt key from the passphrase, random salt and IV, header `PSPBK1`, tag at the end). Reader: decrypt to a temp file, verify the tag before anything is parsed, then list/extract with path checks.
- [ ] Tests (**Review Focus 1, 3**): round trip; wrong passphrase rejected; one flipped byte rejected; truncated file rejected; entries with `..`, absolute paths or links rejected; manifest checksums verified.
- [ ] Commit `feat(backups): encrypted archive format`.

### Task 5: Backups

**Files:** `backup.service.ts`, `backups.controller.ts`, `backup.schedule.ts`, notifications
- Back up (`maintenance` queue, one at a time via a lock): manifest (version, schema migration, created at, contents with sha256), `pg_dump -Fc`, storage files except `exports/` and `backups/`, config (no passphrase; master key only if opted in). Written to `backups/latest.tmp`, verified, then moved to `backups/latest.pbk` (retention one). Status in Redis and `system_setting`. Schedule (default daily 02:00 UTC). Failure → critical notification to platform admins.
- API (`backup.manage`): `GET /api/system/backups` (status), `POST /api/system/backups` (now), `GET /api/system/backups/latest/download` (signed link), `PUT /api/system/backups/schedule`. CLI `cli.js backup [--out file]`.
- [ ] Tests (**Review Focus 1, 2**): backup contains the database and files (restore it into a scratch database and compare), excludes exports and the passphrase; failing `pg_dump` keeps the previous backup and notifies; concurrent requests run once; schedule fires; only `backup.manage` can use the API.
- [ ] Commit `feat(backups): scheduled, verified backups with single retention`.

### Task 6: Restore and maintenance mode

**Files:** `restore.service.ts`, `maintenance.ts`, controller, `cli.ts`, `scripts/perspice`
- Upload (`POST /api/system/restore`, streamed to a private storage key) or CLI (`perspice restore <file>` streams the file into `cli.js restore -`). Check: decrypts and verifies, manifest major version equal and minor ≤ current. Then maintenance mode on (Redis flag; API middleware answers 503 `MAINTENANCE` except health, auth refresh and restore status; ingest keeps buffering to Redis), restore into `perspice_restore`, swap, restore storage files, run migrations, maintenance off, health check, status `done`. Any failure: drop the side database, keep the live one, maintenance off, status `failed`.
- `perspice backup` / `perspice restore` in the host CLI (replacing `db-snapshot`/`db-restore`, which stay as aliases for the database alone).
- [ ] Tests (**Review Focus 3**): round trip restores deleted data and files; newer-version backup refused before maintenance; corrupt archive refused; failure mid-restore leaves the live database intact and lifts maintenance; API answers 503 during maintenance; bats tests for the CLI wrappers.
- [ ] Commit `feat(backups): restore with maintenance mode`.

### Task 9: AWS IoT Core provisioning

**Files:** `apps/server/src/aws/iot-provisioning.ts`, profile `transport: 'aws-iot'`, devices service, web credentials panel
- Profiles gain `transport: 'aws-iot'`. Creating such a device calls `CreateThing`, `CreateKeysAndCertificate`, `AttachPolicy`, `AttachThingPrincipal`; the response carries the certificate bundle (certificate, private key, root CA, endpoint) once. Deleting the device detaches and deletes the certificate and thing. Regenerating credentials rotates the certificate. The platform policy (created by `cli aws-iot-setup`) uses `${iot:Connection.Thing.ThingName}` so a thing can only use its own topics.
- [ ] Tests (`aws-sdk-client-mock`, **Review Focus 4**): calls and their order; the key is not stored anywhere; delete cleans up; the generated policy document restricts topics; the credentials panel shows the bundle once.
- [ ] Commit `feat(aws): AWS IoT Core device provisioning`.

### Task 10: AWS IoT Core ingest, commands and presence

**Files:** `apps/server/src/aws/iot-ingest.client.ts`, `iot-commands.ts`, ingest module, commands publisher
- With `MQTT_TRANSPORT=aws-iot`, ingest connects to the IoT endpoint with its certificate and subscribes to `perspice/v1/+/…` and `$aws/events/presence/+/+`; lifecycle connected/disconnected events drive presence (with the inactivity sweep still in place). Commands publish through `IoTDataPlaneClient.Publish`. EMQX hooks and the EMQX service aren't needed.
- [ ] Tests: against a local MQTT broker playing the IoT endpoint: telemetry is ingested, simulated lifecycle events mark devices online/offline, commands go to the data-plane mock with the right topic and payload, and the ack is processed.
- [ ] Commit `feat(aws): AWS IoT Core transport`.

### Task 11: AWS deployment profile and installer options

Docs cover IAM permissions, policy and costs.

### Task 12: Load test (success criterion 8)
